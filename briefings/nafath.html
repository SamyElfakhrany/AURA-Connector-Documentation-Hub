01 · Board decision

Authorize discovery, not implementation

Nafath is a potential identity capability, not a general employee-service catalog. Official public guidance describes users responding to verification requests through the Nafath application before returning to the integrated service. It does not establish that AURA is eligible to integrate, disclose AURA-ready API details, or provide sandbox access. [1][2]

Recommended board position

Authorize a short discovery phase to identify an accountable Saudi relying-party sponsor, validate the right identity use case, request the approved technical pack and test access, and complete privacy/security review. Return for build approval only when these gates are evidenced.

03 · Product profile

Nafath is a national digital identity and verification experience

SDAIA describes Nafath as an application developed by the National Information Center to help users verify and authenticate digital identities and access integrated government and private-sector services. Public user guidance describes a verification request arriving in the Nafath app, followed by the user completing the verification and returning to the service provider. [1][2]

Biometric verification serviceMay be relevant to a separately authorized high-assurance journey.Whether it is available to AURA, applicable onboarding, supported platforms, and required consent. Do not assume biometric API access. [3]
Important distinction

The reviewed internal document 04-nic.docx is a NIC Java developer guide for person/eligibility, Hajj permit, visitor and worker gateway operations. It lists service-specific hosts, credentials and payloads. It does not describe Nafath relying-party sign-in or the Nafath app verification flow, and should not be used as Nafath API documentation. The project folder contained 14 numbered guides (01-zatca through 14-iata); no Nafath-branded identity integration guide was present in that folder review. [4]

Example Employee Hub journey

Target-state concept, pending provider validation

Employee signs in through the employer’s existing SSO → starts a protected bank-detail change → AURA explains why an additional identity check is needed → AURA hands off through the provider-approved Nafath flow → employee reviews and approves the verification request in the Nafath app → the approved result returns to AURA → AURA records a minimal verification audit event and resumes the HR request. A denied, cancelled, timed-out or unavailable result keeps the HR change pending and offers an approved alternative.

This is a product concept, not a confirmed Nafath protocol. Do not treat identity verification as consent to the underlying HR change; obtain explicit user confirmation for that action.

05 · Integration approach

Secure a provider contract before designing the adapter

The source register recommends an approved identity flow, provider contract before endpoint/auth decisions, and a governed handoff while access is unresolved. No AURA-ready public implementation contract was found. Use a provider-approved protocol and exact security profile once received; do not infer the API from public user instructions or the NIC guide. Required integration handoff pack

  • Named government/provider sponsor and written confirmation of AURA/customer eligibility as a relying party.
  • Approved sandbox and production base URLs, test identities, credentials, certificate and network requirements, and credential rotation procedure.
  • Current technical contract: supported protocol, exact request/response schemas, claims, assurance levels, redirect/deep-link or callback behavior, errors, expiry, rate limits and version policy.
  • Security and privacy documentation: user notice/consent, data-processing terms, retention, logging constraints, incident reporting and security test requirements.
  • Commercial/operational pack: fees if any, SLA/support, onboarding timeline, change notification, production approval and acceptance sign-off.

The public user flow establishes that the user interacts with Nafath and returns to the service. It does not establish endpoint behavior, API authorization, token format, callback security, or entitlement for AURA.

Discovery questions for the provider and business sponsor

  1. Can AURA directly qualify as a relying party, or must an eligible customer or approved integrator own the relationship?
  2. Is the desired product capability login, identity verification, biometric check, transaction approval, or a combination? Which of these are separately supported?
  3. What are the exact onboarding prerequisites, technical protocol, claims, credentials, test identities, sandbox process and security acceptance gates?
  4. What fees, minimums, support SLA, production approval and notice period apply?
  5. Which employee populations and customer tenants are eligible, and what non-Nafath alternatives must be supported?
  6. For the Employee Hub candidate, who owns the protected business action, employee communications, exception handling and audit retention?
