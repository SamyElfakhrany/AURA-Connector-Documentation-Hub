01 · Executive summary

Useful for a specific travel operations workflow, not a broad employee service

Official MOFA evidence

Registration requires organization evidence

The visa platform’s registration form requests company details and named data-entry and approval contacts. Its instructions describe printing and signing the request/agreement, chamber attestation for companies, attaching a commercial registration copy and submitting through official channels. Approval is communicated by SMS.

Internal project evidence

A gateway notification contract is proposed

The project Java guide documents a TIBCO-mediated POST /sendeadata shape with a Bearer service token, external-agent payload and nested business status. It explicitly requires owner-approved sandbox validation; it is not proof that MOFA exposes this route to AURA.

Board implication

Keep scope narrow and gated

Build a secure agent onboarding case-management layer only if a customer needs to manage its own authorized travel agents and the service owner confirms the permitted submission path. Do not position this as visa issuance, employee visa status, or a general MOFA integration.

Decision requestedApprove a short discovery phase to identify the MOFA business owner, TIBCO/API operator, customer eligibility and commercial route. Production implementation is not currently ready to authorize.
02 · AURA use cases

Design for the organization that owns the agent relationship

This is a reusable AURA connector candidate across business applications. Employee Hub can provide a front door for travel-related assistance, but the registration itself belongs to an authorized company or agent administrator, not to an individual employee.

Cross-app: authorized agent onboarding

  • Capture a travel company’s external-agent profile, contacts and evidence against a customer-owned organization record.
  • Route completeness checks and authorized approver sign-off before submission.
  • Send the approved record through the confirmed MOFA channel and preserve a receipt, case reference and current status.
  • Support correction and renewal tasks through an auditable case workflow, only where MOFA confirms these operations are supported.

Employee Hub: travel-service handoff

  • Let employees find the employer’s approved travel desk or agent and request help with a work trip, visa paperwork, or pilgrimage travel.
  • Carry only the minimum request context to the employer’s travel operations team; the employee is not made an MOFA registrant.
  • Show a clear handoff, owner, next step and case status from the employer’s system.
  • Use an external-agent registration connector only behind the organization-facing admin workflow; employee use is indirect and episodic.

Indicative customer experience

  1. Customer travel administrator creates an agent record and uploads approved evidence.
  2. AURA checks required fields and routes the case to an authorized company approver.
  3. On approval, adapter submits once through the owner-confirmed gateway or generates a manual submission pack if that is the approved route.
  4. System stores correlation/reference and response; exceptions go to a reconciliation queue.
  5. Administrator records MOFA decision or completion evidence where no status API exists.

Out of scope

  • Visa application submission, visa issuance, visa-status lookup, visa fees, appointment booking or passport processing.
  • Personal employee visa account access or credential sharing.
  • Claiming registration acceptance based only on HTTP 2xx.
  • Automated renewal, amendment, deletion or status polling unless verified as provider operations.
Terminology controlUse “MOFA external-agent registration connector (proposed)” in board materials. Avoid “MOFA API integration is available” until the exact product owner and access agreement verify that statement.
05 · Integration design

Keep credentials and sensitive agent documents behind an AURA service boundary

The Java guide is a useful technical starting point, not an implementation-ready provider contract. Confirm each item with the MOFA or TIBCO service owner before connecting beyond a local mock.

1 · CaptureAuthorized business admin completes agent profile and evidence
2 · ReviewValidate fields, organization entitlement and sign-off
3 · SubmitBackend adapter sends approved payload using owner-issued token
4 · ReconcileCheck business response, persist reference and status
5 · ResolveQueue exceptions; reconcile before any repeat write

Architecture and contract

  • Use an AURA backend adapter, not a browser/mobile call. Keep Bearer credentials in the managed secret store; rotate by provider policy.
  • Project guide baseline: HTTPS owner-approved base URL, POST /sendeadata, JSON wrapper EA_INFO, Authorization: Bearer ….
  • Parse HTTP outcome and the business envelope separately. Require non-null header.statusDetails.code; treat code 0 as accepted only if provider contract confirms its semantics.
  • Persist AURA operation ID, organization/agent reference, request fingerprint, provider transaction ID, status, attempt count and timestamps.
  • No idempotency header is documented. After timeout or lost response, mark outcome unknown and reconcile with owner/provider before resubmission.

Information security and operations

  • Agent contact details, commercial registration and contracts/certificates are business-sensitive personal and company data.
  • Encrypt in transit and at rest; least-privilege role access; scan uploads; use time-limited download links; define retention and deletion with customer/legal owner.
  • Never log bearer tokens, full payloads, identity details or document bytes. Log correlation IDs and redacted error codes.
  • Separate tenant records and attachments; record consent/authority and approver evidence where required.
  • Apply bounded retry only to safe transient failures approved by owner. Do not automatically retry a registration write after an ambiguous timeout.

06 · Operating model

Make authority and review visible in the product

Customer responsibilities

Confirm the organization qualifies, nominates the authorized registrant and approver, supplies accurate agent data, and owns the signed agreement and supporting documents.

AURA responsibilities

Provide secure capture, role-based approval, validation, controlled submission, status transparency, audit history and case support. AURA does not grant MOFA approval.

Provider responsibilities

Confirm the authoritative endpoint and intermediary, credentials, contract version, business status meanings, availability, support and permitted production use.
