01 · Executive summary

Potentially reusable travel reference data, with provider identity still unresolved

Project guide

Two read operations are described

GET /GetNationalities?PageNumber={page}&PageSize={size} and POST /GetHotels. The hotel body filters on license number, Arabic/English names and city values. Responses use nested response.data.content arrays and pagination metadata.

Identity gap

“Atlas” does not identify the provider

The workbook calls out the operator, data provenance, license and entitlement as unverified. Public search finds an unrelated Saudi renewable-energy Atlas with a similarly generic name. Do not infer that it is the provider in the project guide.

Travel context

Hotels matter in the pilgrimage journey

Nusuk Hajj publicly offers Hajj packages that include accommodation and other travel services. This supports a potential travel workflow context but does not establish ownership, data sharing or technical linkage with Atlas.

Board implicationKeep Atlas in Wave D discovery. Fund a small provider/data-rights check first; do not build a hotel booking journey on top of reference lookups alone.
02 · AURA use cases

Use lookup data to reduce repeated entry across travel workflows

The proposed connector is a shared data utility for AURA apps that manage travel, pilgrimage or accommodation administration. Its likely value is consistent options and identifiers, not end-to-end transactions.

Cross-app: reference synchronization

  • Refresh nationality options with stable code and Arabic/English labels for travel or visitor workflows.
  • Support hotel reference search using license, bilingual name or city fields for authorized travel administrators.
  • Map Atlas identifiers into customer travel forms and reduce duplicate lookup maintenance.
  • Track import time, source/version and record state; identify stale or changed values.
  • Allow configurable paging and scheduled refresh so AURA can reuse cached reference data across multiple apps.

Employee Hub: modest supporting experience

  • Use consistent nationality selection in employee travel, visitor or emergency-contact forms where the customer has a valid business need.
  • Offer employer-controlled hotel discovery only if the dataset is current, licensed and relevant to the employee travel program.
  • Explain that a hotel listing is a reference record, not availability, rate, policy eligibility or booking confirmation.
  • Keep the integration in the admin/support layer until employee demand and data rights justify direct access.

Reference record lifecycle

  1. Obtain an owner-approved service token, base URL and schema.
  2. Fetch nationalities page by page using exact case-sensitive query names.
  3. Fetch hotel records using approved filters and documented page semantics.
  4. Validate the response envelope and provider business status before importing.
  5. Upsert by stable source identifier, preserve last-seen/source metadata and retire records only under an agreed rule.

Out of scope

  • Hotel availability, rates, room inventory and booking confirmation.
  • Payment, cancellation, modification, guest check-in or supplier messaging.
  • Employee identity or visa verification.
  • Assuming an official Nusuk hotel journey consumes this Atlas endpoint.

05 · Integration design

Implement a small read-only adapter after access is proven

The internal guide provides a useful structural contract for two read operations, but the URL, service-token issuer, limits and production entitlement still require provider confirmation.

1 · ConfigureOwner-approved host, base prefix and service token
2 · RequestGET nationalities or POST hotel filters
3 · ValidateCheck response/data/content and provider status
4 · PageContinue to documented final page
5 · UpsertRefresh local reference cache by stable ID

Proposed request contract

  • Authentication: Authorization: Bearer SERVICE_TOKEN; token remains server-side in secret storage.
  • Nationalities: GET /GetNationalities?PageNumber=1&PageSize=100. Preserve exact casing and encode query values.
  • Hotels: POST /GetHotels, JSON body with pageNumber, pageSize, licenseNumber, nameAr, nameEn, cityCode, cityNameAr, cityNameEn.
  • Response guard: validate nested response.data.content, provider status, pagination fields and each item identifier.
  • Do not assume requesting a large page size returns the full dataset. Iterate using documented hasNextPage, page/record metadata.

Cache and reliability pattern

  • Use a backend connector service; do not expose the token or provider URL to browser clients.
  • Separate lookup calls from local cache reads so employee-facing forms remain responsive and provider availability does not block workflows.
  • Upsert nationalities by stable code and hotels by stable provider ID; prevent duplicate records on repeated sync.
  • Store source, last synchronized time, record status and schema version for audit and staleness checks.
  • Apply bounded retry/backoff to idempotent GETs; treat POST /GetHotels as read-only only after owner confirms no side effects.

Configures which travel forms use Atlas data and confirms local policies for displaying, filtering or retaining hotel references.

10 · Board recommendation

Approve Atlas discovery as a low-cost, low-priority lookup candidate

Recommended now

Validate provider identity, entitlement and data fit

  • Ask the project guide owner for the real Atlas vendor/legal operator and API host.
  • Obtain the current guide/spec, sandbox credentials, response examples, page limits and data license.
  • Confirm whether hotel records are current and actionable for the customer’s workflow.
  • Run a 4–7 day discovery and return with validated demand, quality, costs and a revised score.
Hold until evidence

Do not position as hotel booking or official Nusuk API

  • No booking, availability, pricing or reservation API is in the project guide.
  • Official Nusuk Hajj accommodation services do not verify an Atlas integration relationship.
  • Provider identity, access rights, data license, freshness and SLA are not confirmed.
  • Broad Employee Hub deployment is not justified by current reach evidence.
DecisionWave D · Discovery required. Keep the workbook baseline at 29/100 and confidence Low. Advance to a read-only adapter only if a named provider, customer need, permitted data use and approved sandbox are confirmed.
