01 · Board recommendation

Validate one real payment journey before funding production work

Recommendation: keep PayTabs as a build-eligible connector and approve a time-boxed discovery and sandbox pilot. The current AURA connector register places PayTabs at rank 8. The first release should support payment collection for a named AURA workflow, not general payment processing across every tenant by default.

PayTabs can let an AURA application create a payment request, send the customer to a hosted checkout, receive a server-side transaction update, confirm the result, and continue or stop the underlying business workflow. This can remove manual payment links and spreadsheet reconciliation where a real payable journey exists.

The main decision blocker is commercial and operational ownership. AURA must identify the merchant of record, the legal entity receiving funds, the settlement account, the paid service, the refund owner, and the account model. The public fee schedule found is one contract schedule, not a universal API rate card; obtain a current written KSA quote before investment approval.

03 · Connector profile

One payment platform supports several integration patterns

PayTabs is a payment gateway and payments platform for merchants. Its technical portal documents five API integration types: Hosted Payment Page, Invoices, PayLinks, Managed Form, and Own Form. It also documents backend packages including Laravel and Node.js. The regional KSA transaction endpoint is shown as https://secure.paytabs.sa/payment/request. [1][2]

CapabilityWhat it does for an AURA use caseProduct boundary

Invoices and PayLinksCreate a payable link/invoice that can be shared through an approved journey.Useful for payment requests that do not begin inside a live checkout.

Saudi payment methods include mada and other methods that PayTabs lists by market and enables on merchant accounts. Do not promise a method just because it appears in general marketing: exact eligibility, bank sponsorship, currencies, fees, settlement timing, and test access must be confirmed for the selected KSA merchant profile. 06 · Commercial model and cost

Confirm the current KSA rate card before modelling production

PayTabs’ public pricing page currently publishes Paymes SuperApp testing-phase prices in Saudi Arabia, including SAR 49/month, 1% mada, and 2.25% + SAR 1 for credit cards. The page explicitly says those prices are in a testing phase and may change; these are not a confirmed API gateway quote for AURA. [9]

A Saudi Payment Gateway Usage Agreement schedule available publicly lists a one-time SAR 999 setup fee, SAR 199 monthly platform-access fee, and SAR 1 per transaction, excluding VAT. The schedule also describes services such as hosted payment pages, instant notifications, invoices, reports, and integrations. It is a specific published contract schedule and may not apply to AURA or a current account. The agreement allows fee changes with notice. Confirm whether card acquiring/MDR, payment-method charges, refunds, settlement, minimums, and any platform/marketplace charges are additional. [10]

05 · Integration design

Create payment intent, verify result, then fulfil

Start with Hosted Payment Page. PayTabs documents a server-side transaction request that returns a payment-page link. A payer is redirected to that URL and then returned to AURA; a server-to-server callback/IPN reports the payment result. The return-to-browser page is for user experience and must not be treated as proof of settlement. AURA should confirm the transaction with the provider before changing the business request to paid. [2][4][5]

The project guide defines a gateway contract baseline of POST /request to create a payment and POST /query to verify it by transaction reference or cart ID. It sends the server authorization value unchanged in the Authorization header, paired with the merchant profile selected for that payment category. These are guide-level gateway details; confirm the production host, path mapping, auth semantics, required request fields, callback signature, and refund contract with the integration owner and PayTabs before release. The guide’s route list does not define a refund operation. [13]

AURA connector components: tenant-aware connection/profile record; secret reference; payment-intent API; hosted checkout action; callback/IPN endpoint; transaction-query action; canonical payment status model; audit log; reconciliation export; monitoring and finance exception queue. Add a refund action only after its separate contract is confirmed. Keep execution server-side; use only non-sensitive correlation identifiers.

Canonical states: Created, Pending, Authorized (only if the selected flow uses authorization), Paid, Failed, Cancelled, Expired, Partially Refunded, Refunded, and Review Required. Preserve the provider reference and timestamps. Do not translate an unknown provider response into Paid.

07 · Access and controls

Merchant ownership and financial controls are production gates

PayTabs onboarding requests company, trading, bank, ownership, and business documents; the provider says account type and pricing depend in part on estimated monthly sales volume. KSA mada activation requires a Saudi business license or qualifying freelancer certificate, the relevant bank application, and approval by the supported bank. MADA transactions are SAR-only in the cited PayTabs workflow and support sale/refund, but not authorization/capture or recurring payments. [3][8]

Control areaRequired AURA decision or control
Merchant ownershipName the legal merchant of record for every payment flow. Decide whether each customer uses its own PayTabs profile or a centrally contracted model; do not assume submerchant support.
Funds and settlementDocument the bank account that receives funds, settlement timing, reconciliation owner, tax treatment, refund liability, and customer support path.
Payment-data securityUse hosted checkout for MVP. Never log or store PAN/CVV. Store provider keys only in a managed secret store; mask transaction data in logs.
Webhook integrityValidate the provider notification as described in the technical guidance, verify the transaction server-side, and reject unexpected amount, currency, profile, or correlation values. [5][6]
Privacy and retentionMinimize payer data; establish purpose, access roles, retention, deletion, and data-location terms with Legal/Security before production.
Financial operationsSet refund limits and approvals, dispute handling, failed-payment retry rules, month-end reconciliation, and exception ownership.
AvailabilityUse bounded retries, idempotent requests, duplicate-notification handling, timeout recovery, provider status monitoring, and a manual fallback.

This assessment is a product and integration review, not a legal or payment-services authorization. AURA Legal/Compliance must review the KSA commercial structure, consumer/payment obligations, data terms, and any platform or agent role before production.
