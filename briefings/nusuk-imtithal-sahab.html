01 · Executive summary

Operationally useful, but bounded to Hajj service quality workflows

Official ecosystem context

Nusuk Gateway provides an integration enrollment path

The National Portal describes a Ministry of Hajj and Umrah service to unify integration channels and support secure exchange through Nusuk Masar. Organizations register, submit documents, receive approval/verification and then subscribe. This establishes a formal integration channel, not entitlement to this Imtithal/Sahab route.

Project guide evidence

Outbound inspection details are sketched

The internal Java guide specifies a configured complete URL, JSON, X-Client-Id and X-Client-Secret, and an ExternalCrmCreateInspectionDetailsRequest body. It explicitly leaves the response schema and provider acknowledgement rules to the integration owner.

Critical gap

The second direction is not contracted

The portfolio use case mentions sending inspection/incident updates and correlating them to a ticket and employee/location. The guide says inbound ticket creation is a separate API and authentication flow. No endpoint, schema, authorization or lifecycle is supplied for that direction.

Board implicationFund provider and service-owner discovery first. Approve an implementation estimate only after confirming whether AURA will send updates, create tickets, receive status callbacks, or support all three.
02 · AURA use cases

Connect field findings to accountable service operations

Nusuk Imtithal / Sahab is an operational workflow, not a general employee self-service connector. AURA’s value is in routing, approval, case visibility and follow-up for organizations involved in Hajj service delivery.

Cross-app: inspection and incident case flow

  • Link a field visit or inspection finding to the relevant provider, location, service point, ticket and incident.
  • Submit visit outcome, category, status, checklist, comments and permitted attachment references to the named receiving system.
  • Route failed or incomplete submissions into an operational reconciliation queue with a responsible owner.
  • Show activity history and timestamps across field, service desk and customer operations applications.
  • After the inbound contract is approved, support ticket creation or callback updates using the recipient’s authoritative identifiers.

Employee Hub: limited, role-based support

  • Give authorized seasonal inspectors or operations staff a clear queue of assigned follow-up actions, if they are AURA users within the participating organization.
  • Allow supervisors to see unresolved inspection issues, ticket owner, location and next action.
  • Provide notifications and escalation when a case remains unacknowledged; avoid exposing pilgrim or caller identity broadly.
  • Do not expose a public Hajj inspection tool or personal pilgrim ticket handling to ordinary employees.

Candidate outbound payload

The project template includes visit and case identifiers; case/visit status and reason; inspector/supervisor; checklist and comments; visit category/type/date; branch, city, region, district and address; service point/provider/center identifiers; license and declaration details; complaint narrative; attachment IDs; caller name/mobile/NID; and incident identifiers/type.

Schema is a structural template. Requiredness, enumerations, date semantics, attachment rules and privacy basis must be confirmed against current provider documentation.

Product boundaries

  • Not the public Nusuk pilgrim app, Umrah booking, permit issuance, payment or identity service.
  • Not a verified open API or a guaranteed two-way connector.
  • Not a substitute for the official Nusuk Gateway enrollment process.
  • Not an employee-facing personal Hajj service without a separate validated use case.
Identity and namingUse “Nusuk Imtithal / Sahab inspection-to-case integration (proposed)” until the responsible service owner clarifies the system boundary and official product name. “Nusuk Gateway” describes integration onboarding context, not this specific connector contract.
05 · Integration design

Start with a one-way adapter and treat the reverse flow as a separate contract

The internal guide provides enough to define an adapter skeleton. It does not provide an approved endpoint, response model or inbound ticket API. Do not configure real credentials until the integration owner supplies these.

1 · RecordAuthorized inspector completes visit and links ticket/incident
2 · ValidateCheck required fields, lookup codes, attachments and UTC times
3 · QueuePersist an operation and outbox event with correlation IDs
4 · SendPOST JSON to owner-approved full URL using client headers
5 · ReconcileValidate acknowledgement; reconcile before resubmission

Outbound contract from project guide

  • Base configuration: complete inspection-details destination URL, with the path/prefix supplied by the integration owner.
  • Method: POST; Content-Type: application/json; UTF-8; payload type ExternalCrmCreateInspectionDetailsRequest.
  • Authentication headers: X-Client-Id and X-Client-Secret. This guide does not use Bearer OAuth for this direction.
  • The outbound body contains case, visit, geographic/service location, incident, caller and attachment-reference fields.
  • No public route, HTTP response schema, business code catalogue, final receipt or idempotency header is documented.

Inbound ticket contract — separate work

  • Obtain inbound hostname, method/path, authentication, request model, callback/polling model, ticket identifiers and update semantics.
  • Confirm whether tickets are created by AURA or by Sahab, and which system is authoritative for status and ownership.
  • Specify correlation mapping across AURA operation ID, inspection/visit code, case ticket number and incident number.
  • Agree duplicate prevention and replay/reconciliation behavior before enabling automated writes.
  • Do not reuse outbound credentials for inbound calls unless owner approves the scope explicitly.
Timestamp issue in project guideThe sample maps date/time values to LocalDateTime with a literal Z suffix. That can incorrectly label local time as UTC. Confirm timezone policy and serialize an actual UTC instant or offset-aware timestamp before implementation.

06 · Operating model

Protect identity details while preserving operational traceability

Field inspector

Records the visit accurately, links the correct ticket and location, provides allowed attachment references and submits within the agreed time window.

Service supervisor

Owns data quality, approves exceptional corrections, monitors unresolved submission states and coordinates ticket follow-up.

Integration owner

Issues credentials and contract, defines acceptance meaning, publishes supported codes, resolves provider errors and approves production access.
