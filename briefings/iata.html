03 · Product profile

CheckACode validates credentials; it is not an air-booking API

What the API is for

IATA lists CheckACode Web Service as a commercial API for programmatic validation of IATA numeric codes and IATA/IATAN travel agent ID cards. The product page says its agency database covers more than 180,000 travel and cargo agencies and is updated daily. [1]

Where it fits in AURA

Use it behind a vendor/travel-partner onboarding workflow to classify the agency record as verified, invalid, stale, or requiring review. Keep the IATA code, result, freshness, source, and check time auditable.

What it does not establish

A valid code does not by itself prove commercial suitability, contract status, local legal compliance, insurance, current booking rights, or employee-travel policy approval. Keep those decisions with the responsible business owner.

Related IATA products

NDC is a separate airline distribution data-exchange standard for airline offers/orders. CheckACode Professional is a separate manual web app for validating codes. Neither should be represented as the CheckACode API itself. [4][7]

Scope boundaryThis assessment follows the IATA connector row in AURA’s register and the “IATA Agency Code Verification” project guide. It assesses CheckACode only; it does not assess all IATA standards, airline APIs, travel booking, Timatic, or cargo services.

07 · Integration design

Call CheckACode from AURA’s server-side connector

The project guide describes a Java adapter using the gateway base URL, an API key and a service token, followed by GET /checkacode?code={code}. The proposed request has no body. Its sample response is an array with code, last-data-refresh, and reason. The guide says to match each item by code and consider reason = Valid a positive result. These details are the project guide’s gateway baseline, not an independently published IATA API contract; have the integration owner and IATA confirm them before coding to production. [5][6]

Questions to resolve before implementation

  • Is AURA or a customer the licensed subscriber, and does the subscription allow this supplier-onboarding use case?
  • Is the API route direct to IATA or a customer-owned gateway, and who owns its credentials and availability?
  • What exactly counts as valid, stale, invalid, and not found, and how fresh must the data be for vendor approval?
  • Can multiple codes be checked in one call, and what are the call, rate, and retention limits?
  • Does the customer have an employee travel process and approved provider list? Which separate travel platform performs booking and expenses?
