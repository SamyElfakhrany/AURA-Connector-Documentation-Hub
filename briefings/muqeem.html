AURA × Muqeem

Product and integration assessment for a reusable Muqeem connector across AURA applications, with employee mobility and HR journeys as the first product fit to test.

01 · Executive decision

Qualify the Professional API route, then pilot a read-first workflow

Muqeem is an employer service for managing expatriate resident records and completing passport-related transactions. Its official portal markets direct API integration as a Professional-package feature. That materially improves the access outlook versus the connector register’s original assumption, but it does not reveal the API contract or prove that AURA can use it.

Verified product signal

An API tier is advertised

The Muqeem portal describes a Professional package with direct integration between a customer’s internal systems and Muqeem through an API. No public developer specification or AURA onboarding path was verified.

Best first workflow

Resident and visa status visibility

For one employer, test an authorized read and reconciliation of Iqama/resident or visa status and expiry data, only where the approved API exposes those fields.

Keep gated

Sensitive passport transactions

Issuing or cancelling visas, renewing Iqama, changing occupation, or transferring services should remain out of the first pilot until the customer’s legal authority and each API operation are confirmed.

RecommendationStart provider discovery now in parallel with other Saudi access-track work. Build a reusable connector only after a named employer confirms demand and Muqeem/Elm supplies written access conditions, the current API pack, a test route and pricing.
02 · Product and service scope

Employer-led resident administration with tiered access

Muqeem enables establishments to view information about resident employees and complete eligible passport transactions electronically. The portal lists resident and visitor services, reports, subscriptions, operational transactions and payments. Its package tiers have different features; the current portal advertises direct API integration in the Professional package.

Best product boundary

Muqeem is the government-service authority and system of record for its covered passport processes. AURA should orchestrate the employer’s approved workflow, show the returned state and preserve a traceable reference; it should not represent itself as the issuing authority.

Where a shared connector helps

Once approved for a customer, the same governed adapter can serve an HR system, Employee Hub, onboarding portal or case-management app. This is reusable infrastructure for Saudi workforce mobility workflows, not a general connector for every application or every resident record.

05 · Access and onboarding

API availability is advertised; implementation rights remain to be qualified

Evidence found

  • Muqeem presents the Professional package as including direct API integration between the organization’s internal systems and Muqeem.
  • The current public portal describes Basic, Advanced and Professional package tiers and provides self-service registration/package journeys.
  • Muqeem employer services are tied to an establishment account, subscribed package, user roles and authorized operations.
  • The connector register places Muqeem in Saudi Wave D—Discovery with low confidence and explicitly asks whether API access is offered to AURA.

Still to obtain from Muqeem/Elm

  • Written confirmation that a software provider such as AURA may connect for an employer; confirm customer-owned versus platform credentials and per-tenant model.
  • Current API specification: operations, schemas, versioning, authentication, signing or certificates, network requirements, rate limits and error codes.
  • Sandbox/test account, synthetic data, certification steps, production approval and support/SLA.
  • Operation-level terms: who may query, submit, approve, cancel or reverse each transaction; permitted users, employee notice and data handling.
  • Current Professional package eligibility, subscription cost, transaction/report allowances, add-ons, renewal terms and any separate API charges.
1 · Name the customerSelect one Saudi employer, establishment, workforce owner and first workflow.
2 · Qualify package/APIAsk Muqeem/Elm to confirm Professional eligibility, API vendor model and exact supported operations in writing.
3 · Get the technical packRequest current spec, auth model, test credentials, sample records, pricing, SLA and production gate.
4 · Validate securelyTest read-only status and expiry reconciliation, access-denial behavior, stale data, outages and audit history.
5 · Approve a pilotCustomer, provider, security, privacy and legal owners sign off before any live write operation.
Evidence distinction“Muqeem advertises API integration in Professional” is verified. “AURA has a Muqeem API contract, sandbox or production credentials” is not. The advertised package feature is not itself a developer specification or access approval.
06 · Proposed integration design

Keep employer authority in the tenant boundary

AURA should build a customer-scoped adapter only after the provider confirms the API contract. The following is a target design, not a statement about Muqeem’s actual protocol or permissions.

LayerAURA responsibilityProvider/customer confirmation
Establishment and planBind each AURA tenant to the correct Saudi establishment, active package, approved workflows and employer data owner.Who contracts and pays? Can the customer authorize AURA as processor/integrator? Does every establishment need a separate subscription/API client?
Identity and authorizationMap AURA employee key to the minimum Muqeem identifiers needed for a permitted read/action. Keep employer HR roles distinct from employee Hub views.Confirm identifier types, role scopes, employee consent/notice needs, approvals and whether delegation is supported.
Credential securityStore provider-issued credentials in a managed secret store; isolate by customer, log access and rotate on schedule.Use the specified authentication, certificate or signing mechanism. Do not assume OAuth, API keys or mTLS until documented.
Adapter and data modelNormalize only approved resident/visa data into AURA’s canonical status model. Keep the raw provider record out of general app data.Confirm API schemas, definitions, time zone/date handling, field meanings, pagination, update timestamps, limits and version changes.
Workflow writesFor later writes, show a pre-submit summary, verify employer authority, capture required approval and persist a transaction reference/state.Confirm which operations are supported, mandatory attachments, statutory fee handling, validation, cancellation and reversal behavior.
Failure and reconciliationDistinguish accepted, pending, rejected, unknown and expired status. Do not replay an uncertain write; reconcile by provider reference first.Confirm idempotency, status lookup, retry rules, delayed/batch results, outage support and reconciliation SLA.
Employee HubShow approved employee-specific status and expiry alerts; provide an official handoff when direct self-service is not available.Confirm whether a company API response may be shown to the employee, freshness label, permitted purpose and employee access process.

First-pilot scope

  • One employer establishment and one test environment.
  • One read-only resident/visa status workflow if offered in the API.
  • Field-level mapping to HR records plus expiry and stale-data exceptions.
  • Admin-only dashboard first; Employee Hub view only after permission review.

Product controls

  • Strict customer separation, least privilege and full audit for reads, exports and actions.
  • Mask resident identifiers and avoid raw personal data in logs.
  • Display data source and “last checked” timestamp; do not imply real-time truth where sync is delayed.
  • Keep manual official-portal path for unhandled cases and outages.

10 · Board recommendation

Start API qualification now; authorize only a narrow read-first pilot

Proceed now

Access discovery

Use the advertised Professional API feature to request AURA eligibility, current spec, sandbox, pricing, supported objects and a named employer sponsor.

Pilot option

Resident status and expiry

Test a read-only HR workflow for one employer, with a clear freshness label, exception handling and employee experience only where permitted.

Hold

Broad transaction automation

Do not commit to visa/Iqama execution, bulk updates or universal employee self-service before the exact API permissions and legal/process controls are verified.

Portfolio conclusionMuqeem is strategically relevant to Saudi employers and has a credible API product path, so it deserves active discovery. Keep the internal Wave D designation until AURA’s access and technical readiness are evidenced. If no direct path is approved, launch a useful employee handoff journey without API claims.
