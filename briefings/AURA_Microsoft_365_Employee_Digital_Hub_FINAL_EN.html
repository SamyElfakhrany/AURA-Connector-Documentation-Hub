01 · Definition

What Aura is building—and why

Microsoft 365 is strategically strong for Aura because it already contains the employee’s identity, calendar, tasks, files and collaboration context. Aura should sit above it as the employee experience and orchestration layer—not copy it.

Microsoft Entra ID

Authentication, tenant identity, tokens, consent and access policy.

Microsoft Graph

The API gateway Aura uses for approved Microsoft 365 resources and actions.

Aura

The context layer that organizes work around the employee, project, knowledge, workflows and AI.

Core product principleMicrosoft remains the system of record for Microsoft data. Aura stores mappings, workflow state and the minimum data required for the employee experience.

05 · Technical integration

How Aura should register and integrate

Recommended architecture: Aura authenticates through Entra, acquires Graph tokens through MSAL, calls Graph from the backend, normalizes approved data and exposes it to Aura apps. Avoid storing broad Microsoft content when a source link or on-demand read is sufficient.

App registration & customer onboarding steps

Choose tenancy model

Single-tenant for an internal/private pilot; multitenant organizational app for SaaS serving multiple customers.

Register Aura in Entra

Identity → Applications → App registrations → New registration; capture the client and object identifiers.

Configure authentication

Add exact redirect URIs; use authorization code flow and PKCE where applicable.

Credentials + permissions

Use MSAL; prefer certificate/federated credentials in production; request the least Graph scopes.

Consent + validation

Obtain admin consent where required; test tenant isolation, revocation, 403/429 and audit before production.

Recommended SaaS modelOne multitenant organizational Aura app, with consent/service principal created in each customer tenant. Aura keys every request by customer/tenant and isolates tokens, configuration and data. Per-customer app registrations remain an optional enterprise-isolation choice, not a universal requirement.

Connector runtime design

Identity mapping

Persist Aura customer ID + Microsoft tenant ID + immutable user object ID. Never use email alone as the stable identity key.

Read path

Use on-demand reads first, $select only required fields, follow @odata.nextLink, and cache only what the UX truly needs.

Write path

Require user confirmation. Store Aura request ID + Microsoft resource ID + outcome; reconcile ambiguous timeouts before retrying non-idempotent creates.

Sync path

Add delta queries or change notifications only for approved freshness needs; renew subscriptions and design recovery for missed events.

Reliability

Honor Retry-After for HTTP 429, handle 401/403/404 explicitly, use bounded retries with jitter, and monitor Graph latency/error rates.

Disconnect

Provide an admin disconnect/revoke flow, stop subscriptions/background jobs, and delete or expire local tokens/sync state according to retention policy.

07 · Security, privacy & Saudi controls

Security, privacy and Saudi compliance considerations

Security is primarily a permission and data-minimization problem. Start delegated, request the smallest scopes, isolate every customer tenant and design every stored field/retention rule deliberately.

Aura technical controls

  • Delegated first: employee-facing journeys should use the signed-in user context unless a justified background requirement exists.
  • Least privilege: request the lowest permission per operation; feature-gate functionality when a permission is not granted.
  • Selected scopes: for background SharePoint/OneDrive access, prefer Sites.Selected or newer selected-operation scopes instead of tenant-wide read/write.
  • No legacy ACS: SharePoint Azure ACS app-only stopped working on 2 Apr 2026; use Entra application permissions.
  • Secrets: keep tokens/credentials server-side; prefer certificates or federated credentials over long-lived shared secrets for production.
  • Data minimization: do not log access tokens, mailbox bodies or full file content; store references and the minimum metadata required.
  • Tenant isolation: key all integration state by Aura customer + Microsoft tenant and prevent cross-tenant token/data reuse.
  • Resilience: honor Retry-After for 429, use delta/change notifications where available, and reconcile uncertain writes before retry.

Customer decisions before storing data

  • Data classification and approved fields.
  • Retention, deletion, export and support access.
  • Actual licensed workloads: Teams, Planner, Bookings, Shifts, Copilot, etc.
  • Consent, Conditional Access and DLP/Purview policies where applicable.
  • Aura hosting location and whether any personal-data transfer outside KSA actually occurs.

PDPL / cross-border transfers

Personal-data processing and transfers outside KSA must be assessed under PDPL and its transfer regulation. Do not treat “cloud integration” as an automatic legal basis.
